# Reproducible browser campaign

The root `vp run test` acceptance task runs the complete table Chromium browser suite after the table fast suite. The full 200,000-row Kafka campaign remains a separate `vp run test:e2e` gate and builds the packages it needs once within that task.

Run `vp run test:e2e` for exactly **200,000 distinct identities per topic**, 400,000 total, or `python3 scripts/e2e.py --smoke 100` for a distinctly labelled development smoke. Smoke is never full acceptance. `--no-build` is permitted only for explicit smoke runs and reuses native release binaries; the web application is built for the new isolated run and served with its production preview handler. The default deadline is 30 minutes. All failures are nonzero, retained, and never changed into skipped passes. Every owned cleanup action is attempted even if another cleanup fails; acceptance is computed only after teardown, and any cleanup failure makes the campaign fail.

The runner creates a new owned broker namespace through `scripts/kafka.py`, two source topics with two partitions each, and their state topics. It owns each native/web/browser/producer child and stops only those children and the broker it created. Raw producer submissions and delivery receipts, source cuts, browser observations, memory samples, logs, and a result summary remain in `.local/e2e/<run>/`. Do not commit these bulk artifacts. The source digest is taken before any native/web build and checked after native build, before and after web build, and after browser execution; editing the candidate invalidates full acceptance. A development smoke can finish with `candidateFrozen: false` and remains explicitly unqualified for full acceptance. The Kafka broker helper verifies ownership before lifecycle operations. Broker data is retained for diagnosis after shutdown.

One persistent release producer performs both the initial batched seed and live mutations. The oracle tracks current identities from acknowledged keys and values. Browser completeness is compared with a SHA-256 of every actual materialized client row's order ID, authoritative row ID and complete business payload, including exact integer/decimal strings and absent versus null fields. Native durable, derived, and serving cuts must all reach the producer's next offset on each required partition before a coherent result is accepted. Fetched progress alone never qualifies. Before launching the browser, a bounded native catchup phase verifies those cuts plus exactly 200,000 active rows per source, with raw health samples retained. This separates initial source ingestion from browser acquisition; the full browser campaign still commits an update while Client acquisition is incomplete.

The application diagnostics are enabled only by `VITE_RVS_E2E=1`. They expose actual hook state and a bounded production-provider query adapter. UI Quick Filter and deep scroll use real grids; the bounded numeric, grouping, sorting and facet probes use the same native service and Worker, but are explicitly not evidence for the corresponding menu interaction. Worker instrumentation records cumulative result rows, maximum window size, and distinct delivered identities before probes to distinguish sparse delivery from sparse DOM rendering. The cumulative initial delivery bound remains 1,000 rows. It also verifies termination when the provider is disposed.

The campaign covers full client fingerprints, independent Unicode Quick Filters, Match None, row 199,999, exact numeric range, multiple sort keys, group count/sum/average, all 2,048 distinct customer facets, actual Client cell editing, clipboard paste, vertical drag fill, atomic committed saves, concurrent source/draft conflict, selected-row identity across reordering, identity-preserving upsert, deletion, mutation during partial bootstrap (full campaign), same-page connection interruption, owned native restart followed by a later update (with an explicitly recorded same-page browser retry if the unchanged automatic reconnect policy is exhausted), distinct Worker asset failure and explicit retry, and disposal. Expected exact averages are calculated with integers from the seed formula. Timings use each process's own monotonic clock; byte counts are encoded HTTP bytes from the page and actual binary WebSocket payload lengths measured inside the remote Worker, with complete-source and viewport frame totals reported separately. Page CDP WebSocket counts are labelled separately because page sessions do not observe the Worker socket. Raw bounded requestAnimationFrame intervals include an explicitly labelled estimate of missed 60 Hz opportunities; they do not measure physical dropped paints. Effective broker/topic configuration and actual two-partition admission are retained. CDP memory metrics and native RSS are samples, not physical-paint, end-to-end causal latency, production SLA, or throughput claims.

`result.json` keeps `charterAcceptance: false`: this runner is a concrete campaign gate, not a declaration that every charter requirement passed. `fullCampaignAcceptance` is true only when this complete browser campaign passes with 200,000 rows per topic and unchanged candidate source. Full semantic/native-WASM parity and the other repository gates must also pass on the frozen candidate. The browser result lists its exact completed checks; no omitted test is silently represented as passing. This harness has no browser download step. If a browser installation is needed, use `PLAYWRIGHT_SKIP_BROWSER_GC=1` to preserve other projects' browser caches.

All supported demo writers share one persistent, journaled control authority. `scripts/seed.py` sends an authenticated `/seed` request to the running owned control instead of creating a second producer. The control holds a config-scoped process lock; its native producer holds a separate mandatory config-scoped writer lock. A second native producer is rejected; the binary also refuses to run without the live control-authority lock. The campaign tests both rejection paths. Each batch uses a Kafka transaction and receipts are exposed only after commit. The native generated schema admits the original JSON as well as the encoded protobuf so unknown fields cannot disappear while surviving in the optimistic journal. A durable prepared intent without a corresponding committed receipt fences subsequent writes and recovery. This is an optimistic concurrency contract for the supported private demo writer paths, not a general Kafka compare-and-swap service for third-party writers.

Run the Kafka-free control regressions with `python3 -m unittest discover -s tests/integration -p '*_test.py'`. They cover stale saves after the public seed path, whole-batch conflict prechecks, identity invariants, exact scalar/null values, authorization/origin/request bounds, ambiguous receipts, startup timeout cleanup and uncertain journal replay.

Restart qualification independently awaits the new native instance and all acknowledged durable, derived, and serving cuts with exact source counts, retaining raw health samples and elapsed catchup time. If the browser reports a terminal `recovery-attempts` or `recovery-budget` failure, the harness records its truthful error states, retry count and recent recovery events, then uses the existing Reconnect and reacquire button on the same page. That outcome is labelled explicit retry, never automatic restart recovery. The separate transport-interruption test still requires automatic recovery. Product recovery defaults are unchanged.
