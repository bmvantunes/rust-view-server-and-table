# Reproducible browser campaign

Run `vp run test:e2e` for exactly **200,000 distinct identities per topic**, 400,000 total, or `python3 scripts/e2e.py --smoke 100` for a distinctly labelled development smoke. Smoke is never full acceptance. `--no-build` only reuses native release binaries; the web application is built for the new isolated run and served with its production preview handler. The default deadline is 30 minutes. All failures are nonzero, retained, and never changed into skipped passes.

The runner creates a new owned broker namespace through `scripts/kafka.py`, two source topics with two partitions each, and their state topics. It owns each native/web/browser/producer child and stops only those children and the broker it created. Raw producer submissions and delivery receipts, source cuts, browser observations, memory samples, logs, and a result summary remain in `.local/e2e/<run>/`. Do not commit these bulk artifacts. The source digest is taken after the web build and must remain unchanged through browser execution; editing the candidate invalidates a run. The Kafka broker helper verifies ownership before lifecycle operations. Broker data is retained for diagnosis after shutdown.

One persistent release producer performs both the initial batched seed and live mutations. The oracle tracks current identities from acknowledged keys and values. Browser completeness is compared with a SHA-256 of every actual materialized client row's order ID, authoritative row ID and complete business payload, including exact integer/decimal strings and absent versus null fields. Native durable, derived, and serving cuts must all reach the producer's next offset on each required partition before a coherent result is accepted. Fetched progress alone never qualifies.

The application diagnostics are enabled only by `VITE_RVS_E2E=1`. They expose actual hook state and a bounded production-provider query adapter. UI Quick Filter and deep scroll use real grids; the bounded numeric, grouping, sorting and facet probes use the same native service and Worker, but are explicitly not evidence for the corresponding menu interaction. Worker instrumentation records actual delivered result cardinality before probes to distinguish sparse delivery from sparse DOM rendering. It also verifies termination when the provider is disposed.

The campaign covers full client fingerprints, independent Unicode Quick Filters, Match None, row 199,999, exact numeric range, multiple sort keys, group count/sum/average, all 2,048 distinct customer facets, identity-preserving upsert, deletion, mutation during partial bootstrap (full campaign), same-page connection interruption, owned native restart followed by a later update, distinct Worker asset failure and explicit retry, and disposal. Expected exact averages are calculated with integers from the seed formula. Timings use each process's own monotonic clock; byte counts are browser-observed encoded HTTP and WebSocket payload bytes. CDP memory metrics and native RSS are samples, not physical-paint, end-to-end causal latency, production SLA, or throughput claims.

`result.json` keeps `charterAcceptance: false`: this runner is a concrete campaign gate, not a declaration that every charter requirement passed. Client editing/paste/fill/save/conflict and moved selection, full semantic/native-WASM parity, and the other repository gates must also pass on the frozen candidate. The browser result lists its exact completed checks; no omitted test is silently represented as passing. This harness has no browser download step. If a browser installation is needed, use `PLAYWRIGHT_SKIP_BROWSER_GC=1` to preserve other projects' browser caches.

All supported demo writers share one persistent, journaled control authority. `scripts/seed.py` sends an authenticated `/seed` request to the running owned control instead of creating a second producer. The control holds a config-scoped process lock; its native producer holds a separate mandatory config-scoped writer lock. A second native producer is rejected and the campaign tests that rejection. Each batch uses a Kafka transaction and receipts are exposed only after commit. The native generated schema admits the original JSON as well as the encoded protobuf so unknown fields cannot disappear while surviving in the optimistic journal. A durable prepared intent without a corresponding committed receipt fences subsequent writes and recovery. This is an optimistic concurrency contract for the supported private demo writer paths, not a general Kafka compare-and-swap service for third-party writers.

Run the Kafka-free control regressions with `python3 -m unittest discover -s tests/integration -p '*_test.py'`. They cover stale saves after the public seed path, whole-batch conflict prechecks, identity invariants, exact scalar/null values, authorization/origin/request bounds, ambiguous receipts, startup timeout cleanup and uncertain journal replay.
